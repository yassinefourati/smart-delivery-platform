# API documentation

**One Swagger UI for the whole platform, at the gateway:
[http://localhost:8080/swagger-ui.html](http://localhost:8080/swagger-ui.html).**

The dropdown at the top right switches between services. Every document in it is
generated by the service that owns the API, so nothing here can drift from the real
controllers.

```
                      browser
                         |
                         v
   +---------------------------------------------+
   |  api-gateway :8080                           |
   |    GET /swagger-ui.html      <- the only UI  |
   |    GET /v3/api-docs/swagger-config           |
   |    GET /v3/api-docs/<service> -- proxied ----+---> <service>:<port>/v3/api-docs
   +---------------------------------------------+
```

## Why it is only at the gateway

Every service has had springdoc since its own phase, and each still serves
`/v3/api-docs` and a Swagger UI on its own port. Those are now an implementation detail:
in the compose stack the service ports are published for debugging, and in any real
deployment they would not be reachable at all. The gateway is the only address a client
is ever given (see [architecture.md](architecture.md)), so it is the only place API
documentation is any use.

There is a second reason, and it is the one that decided the design. Swagger UI's "Try it
out" button issues a real HTTP request from the browser, to whatever the document's
`servers` entry says. Left to itself, springdoc derives that entry from the request that
fetched the document — which here arrives *from the gateway*, so order-service's document
would advertise `http://order-service:8084`: a hostname that exists only on the compose
network and resolves to nothing in the reader's browser. Every call would fail with an
opaque network error, from a UI that otherwise looked perfectly fine.

So each service pins its `servers` entry to the gateway's public URL, via
`platform.openapi.public-url` (see below). One entry, not two: reaching a service
directly bypasses the gateway's routing, correlation id, and error handling, and offering
it in a dropdown would present that as a supported way in.

## How the aggregation works

Two halves, both in `api-gateway/src/main/resources/application.yml`.

**The UI** is configured with an explicit list of documents rather than its own:

```yaml
springdoc:
  swagger-ui:
    path: /swagger-ui.html
    urls-primary-name: user-service
    urls:
      - name: user-service
        url: /v3/api-docs/user-service
      # ... one per service
```

The URLs are relative, so the browser fetches them from the gateway's own origin and
there is no CORS configuration to get wrong.

**The routes** turn each of those URLs into a call to the owning service:

```yaml
- id: order-service-api-docs
  uri: ${ORDER_SERVICE_URI:http://localhost:8084}
  predicates:
    - Path=/v3/api-docs/order-service
  filters:
    - SetPath=/v3/api-docs
```

Note the predicate is an **exact path**, not `/v3/api-docs/**`. Swagger UI fetches its own
settings from `/v3/api-docs/swagger-config`, which springdoc serves from the gateway
itself; a wildcard would swallow that request, route it to user-service, and the UI would
come up empty with nothing in the log to explain why.

Adding a service to the picker is therefore two blocks of YAML in one file, and no code.

## Per-service document metadata

The parts springdoc cannot infer — title, version, the server URL, and the bearer
security scheme — come from `platform-starter`'s `PlatformOpenApiAutoConfiguration`
(see [ADR 009](adr/009-platform-starter-and-the-shared-code-boundary.md)), configured per
service:

```yaml
platform:
  openapi:
    title: order-service API
    description: Order placement, the saga, and cancellation
    version: v1
    public-url: ${PUBLIC_GATEWAY_URL:http://localhost:8080}
```

All four have defaults — `title` falls back to `spring.application.name` — so a new
service is documented correctly with no configuration at all.

A service that genuinely needs an unusual document (a second server, another security
scheme) declares its own `OpenAPI` bean and the auto-configuration steps aside.

## Authenticating in Swagger UI

Everything except registration and login requires a JWT
([docs/security.md](security.md)), so the document declares a bearer scheme and the UI
shows an **Authorize** button.

1. `POST /api/v1/users` (user-service) to register, or use an existing account.
2. `POST /api/v1/auth/login` to get an `accessToken`.
3. Click **Authorize**, paste the token value **without** the `Bearer ` prefix — Swagger
   UI adds it — and every subsequent "Try it out" is authenticated.

The token is an RS256 access token verified against user-service's published JWKS
([ADR 007](adr/007-asymmetric-jwt-signing.md)); the same token works across every service
in the picker, which is the point of it being signed rather than shared.

## Error responses

Every error in the platform is an RFC 7807 `application/problem+json` body
([ADR 009](adr/009-platform-starter-and-the-shared-code-boundary.md)):

```json
{
  "type": "https://github.com/yassinefourati/smart-delivery-platform/blob/main/docs/security.md#error-codes",
  "title": "NOT_FOUND",
  "status": 404,
  "detail": "Order 3f2a... not found",
  "instance": "/api/v1/orders/3f2a...",
  "timestamp": "2026-03-04T10:15:30.123Z",
  "error": "NOT_FOUND",
  "message": "Order 3f2a... not found",
  "path": "/api/v1/orders/3f2a...",
  "correlationId": "9c1d..."
}
```

The last five fields are the pre-Phase-19 body, kept verbatim as RFC 7807 extension
properties so that nothing which parsed the old shape has to change. See
[security.md](security.md#error-responses).

## What is not here

**A published, versioned API spec.** The documents are generated at runtime from the
running services; there is no `openapi.yaml` checked in, no spec-first workflow, and no
CI check that the API has not changed incompatibly. For a platform with external
consumers that would be the obvious next step — generate the documents in CI, diff them
against the previous release, and fail on a breaking change. With no external consumers
yet, it would be ceremony around a contract nobody depends on.
