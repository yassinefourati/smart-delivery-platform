 1. WHAT THIS CHART DID NOT CREATE, AND WILL NOT
--------------------------------------------------------------------------------
No Postgres, no Kafka, no Redis. Those are managed services, or operator-managed
clusters (CloudNativePG, Strimzi), and the definitions of them in
docker-compose.yml are for local development only -- a single-instance Postgres
with one superuser and a Kafka broker in KRaft mode with no replication is the
right shape for a laptop and the wrong shape for anything else. It also does not
install Prometheus, Grafana, Tempo or an OTel Collector; it only points at them
and, optionally, registers a ServiceMonitor and a PrometheusRule with an Operator
that already exists.

 2. SECRETS
--------------------------------------------------------------------------------
{{- if .Values.secrets.create }}
secrets.create is TRUE, so this release just created Secrets full of
REPLACE_ME placeholders. They are there to show the shape and to let
`helm template` prove the wiring; Postgres will reject them and JwtKeyProvider
will throw on a PEM that is not one. That failure is correct -- a service that
cannot sign or verify tokens must fail to start rather than mint garbage -- but it
means this release cannot work until you replace them. Prefer secrets.create=false
and the commands below.
{{- else }}
secrets.create is false, which is the recommendation: the chart holds no
credential and never should. Create these yourself, in this namespace, before the
pods can leave CreateContainerConfigError:
{{ range $secretName, $data := .Values.secrets.placeholders }}
  {{ $secretName }}: {{ keys $data | sortAlpha | join ", " }}
{{- end }}

  # The signing key -- generate out of band, never commit it.
  openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out sdp-signing-key.pem
  kubectl -n {{ .Release.Namespace }} create secret generic sdp-jwt-signing \
    --from-file=JWT_PRIVATE_KEY=./sdp-signing-key.pem

  # A database credential. --from-file, not --from-literal: a literal lands in
  # the shell history.
  kubectl -n {{ .Release.Namespace }} create secret generic sdp-user-db \
    --from-literal=DB_USERNAME=user_service_role --from-file=DB_PASSWORD=./user-db-password.txt

An External Secrets Operator syncing from AWS Secrets Manager, GCP Secret Manager,
Azure Key Vault or Vault produces an ordinary Secret, so nothing in this chart
changes when that lands -- keep the names above and it is a drop-in.
{{- end }}

A Kubernetes Secret is base64, not encryption. `echo <value> | base64 -d` is the
whole protection: anyone with `get secrets` here has every plaintext, and so does
anyone with an etcd backup. RBAC is the actual control.

 3. user-service IS PINNED TO ONE REPLICA
--------------------------------------------------------------------------------
secrets.jwtSigningKeyProvisioned is false, so the chart will refuse to render more
than one user-service replica. That is not caution for its own sake. With no
JWT_PRIVATE_KEY, JwtKeyProvider generates a DIFFERENT throwaway RSA key in every
replica and publishes them all under the SAME kid -- and Spring Security refetches
a JWK set only on an UNKNOWN kid, so a verifier that cached the wrong pod's key
returns an invalid-signature 401 it cannot recover from. Roughly (N-1)/N of tokens
fail, per verifier, and the failing set reshuffles every time a cache expires. It
does not stop at logins: order-service's SERVICE token fails at inventory-service,
a 401 is not in that circuit breaker's ignore-exceptions, and the breaker opens --
so a missing signing key reads on the Grafana dashboard as inventory-service being
down.

  1. provision sdp-jwt-signing (above);
  2. set services.user-service.config.JWT_SIGNING_KID to a real generation label,
     e.g. sdp-2026-04-a -- never the sdp-dev-key-1 default, which ends up stamped
     in every production token's header;
  3. set secrets.jwtSigningKeyProvisioned=true, then raise the replica count.

One replica also means: no PodDisruptionBudget for user-service (a PDB there would
hang every node drain), and a rolling update logs everyone out, because tokens
signed by the replaced pod's ephemeral key stop verifying.
{{ end }}

 4. PREREQUISITES IN THE APPLICATION CONFIG THAT THIS CHART CANNOT CHECK
--------------------------------------------------------------------------------
All of these were verified present in the services' application.yml when this chart
was written. The list is here for the future where one is reverted, or a service is
added without them -- each entry is the symptom, not a to-do.

a) THE PROBE PATHS MUST BE PUBLIC. All three probes target
   /actuator/health/liveness and /actuator/health/readiness, and
   requestMatchers("/actuator/health") matches that path and NOTHING below it. If
   the six services with a SecurityConfig do not list both probe paths in
   PUBLIC_ENDPOINTS, the kubelet gets a 401, reads it as a failed probe, and every
   one of those six restarts on a failureThreshold cadence forever -- while
   api-gateway and notification-service, which have no security starter, stay up.
   It looks like a cluster fault and it is a one-line authorization problem.
   Check it the moment the pods are up:

     kubectl -n {{ .Release.Namespace }} exec deploy/{{ $gwName }} -- \
       wget -qO- http://user-service:8081/actuator/health/readiness

b) /actuator/prometheus must be public for the same reason, or six of eight scrape
   targets return 401 and those panels are blank with nothing saying why.

c) management.endpoint.health.probes.enabled must be true, and the two groups must
   be liveness: livenessState and readiness: readinessState. Note that turning
   probes on also registers those two contributors in the DEFAULT group, so the
   aggregate /actuator/health now returns 503 during shutdown and before
   ApplicationReadyEvent -- harmless here, but worth knowing if anything alerts on
   it.

d) FLYWAY_CONNECT_RETRIES, FLYWAY_CONNECT_RETRIES_INTERVAL and
   FLYWAY_LOCK_RETRY_COUNT are set by this chart but only bind if the services'
   application.yml declares them. Without that, they are silently ignored and a
   pod scheduled seconds before Postgres is ready crashloops instead of waiting.

e) SHUTDOWN_PHASE_TIMEOUT likewise, plus SCHEDULER_POOL_SIZE on the four services
   with @EnableScheduling. terminationGracePeriodSeconds is validated against the
   phase timeout this chart sets, so if that placeholder disappears the grace period
   is consistent with a number the application no longer reads.
